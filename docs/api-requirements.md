# Вимоги до API контенту (етап 1: статичні сторінки)

Цей документ — технічне завдання для бекенду: які ендпойнти потрібні редактору
й проду, які схеми даних вони віддають/приймають, і чому саме так. Мета —
щоб бек не придумував зайвого: усе, що редактор зберігає у `blocks` та у
файлах налаштувань (`global.json`, `palette.json`, `menu-content.json`) —
**непрозорий JSON-блоб**, бек його тільки зберігає й повертає байт-у-байт,
без власної схеми/валідації/перетворення. Це критично: кожне нове поле чи
тип блоку, який додасть редактор, інакше стає бекенд-міграцією.

Область цього етапу — тільки статичний контент:
`public/files/theme_2/dynamic-pages/*.json`, `palette.json`, `global.json`,
`menu-content.json`, `public/files/theme_2/styles/*.css`,
`public/images/theme_2/**`. Кабінет-варіанти (
`account-pages.json`) — окрема, поки суто редакторська механіка, у цей етап
не входить.

**Це нові ендпойнти, не розширення існуючого `/content/public/...`.** У
компанії вже є робочий контент-домен на цьому шляху — перевірено наживо на
dev-бекенді, розділ 0 фіксує, що саме там є. Але його схема
даних не підходить (не opaque-блоб, як описано вище) — тому весь контракт
нижче описує НОВІ ендпойнти, які бек має зробити з нуля під ці вимоги. Поки
вони не готові, редактор працює тільки в локальному демо-режимі
(`VITE_API_REQUEST_MODE=test`, IndexedDB); коли бек їх викотить —
переключаємось на `live` і звіряємось. (На випадок збою чи ще не готового
ендпойнта редактор і в `live`-режимі тихо падає назад на локальні дані з
попередженням на екрані — тому це не блокер для поступової викатки частинами,
можна здавати по одному ендпойнту, а не все одразу.)

**За результатами перемовин з беком: усі нові ендпойнти теж живуть під
`/api/content`.** Це не той самий `/content/public/...` з розділу 0 — той
залишається старим і не чіпається. Новий `/content` — спільний префікс,
під ним ті самі типізовані під-ресурси, що й описані нижче
(`/content/pages/...`, `/content/settings/...`, `/content/styles/...`,
`/content/images`), а не єдиний плаский `{key}`, як у старій системі. Кожна
адреса нижче в цьому документі вже показана з цим префіксом.

## Статус (оновлено 2026-09-02)

✅ **Увесь контракт цього етапу готовий і підключений на клієнті.**
`GET/PUT/DELETE /content/pages/{slug}`, `GET /content/pages`,
`PATCH /content/pages/{slug}/visibility`, `POST /content/images`,
`GET/DELETE /content/images/{name}`, `GET/PUT /content/settings/global`,
`GET/PUT /content/settings/seo`, `GET/PUT /content/settings/palette`,
`GET/PUT /content/settings/menu-content`, `GET /content/styles`,
`GET/PUT /content/styles/{name}`.

Два останні пункти (`/content/styles/*` і `/content/settings/menu-content`)
до 2026-08-24 значились як «⏳ ще ні». Бек їх викотив — перевірено наживо
проти живого dev-API 2026-09-02: усі чотири GET
відповідають 200 з реальними даними, а `GET /content/styles/{name}` приймає
ім'я і з розширенням, і без (`faq` та `faq.css` віддають той самий файл).
**Не залишайте цей розділ протухати:** саме застарілий рядок «⏳ ще ні»
згодом призвів до висновку, що редактор працює через фолбек, хоча він давно
працює наживо.

Фолбек на IndexedDB/`public/` нікуди не подівся — він спрацьовує лише коли
запит реально впав, і показує попередження на екрані (див. нижче). Тобто
мовчазного відкату «як у демо-режимі» не буває: якщо дані локальні, це
видно.

## 0. Що вже є на існуючому `/content/public/...` (для довідки, не як ціль)

Розвідка наживо на dev-бекенді (Hyperf/PHP-бекенд), щоб не
вигадувати вимоги в вакуумі — реальні приклади нижче корисні як довідка про
формат даних (`TemplatePageModel`, `GlobalSettingsModel` і т.д. вже саме
такі на практиці), але сам шлях `/content/public/{key}` і його схема — НЕ
те, під що пишеться цей контракт (навіть попри спільний префікс `/content` -
новий контракт нижче має типізовані під-ресурси `/content/pages/...`,
`/content/settings/...` і т.д., а не один плаский `/content/public/{key}`).

| Ключ | Приклад | Є? |
|---|---|---|
| `{pageId}` | `GET /content/public/bus-park` | так, повертає `{id, breadcrumbs, backButton, hero, blocks}` |
| `footer-content` | `GET /content/public/footer-content` | так, той самий формат |
| `global-settings` | `GET /content/public/global-settings` | так |
| `main-menu` | `GET /content/public/main-menu` | так |
| `styles/{name}` | `GET /content/public/styles/root.css` | так, CSS текстом |
| `palette` (і варіанти назви) | `GET /content/public/palette` | ні |
| список сторінок | — | ні, жодного варіанту |

Формат помилки для неіснуючого ключа там — **HTTP 200**, тіло
`{"success":false,"error":"Page not found"}` (не 404). Для геть
незареєстрованого шляху — SPA-фронтенд бекенду віддає свій `index.html`,
теж з 200. Це вже застаріле — новий контракт нижче не зобов'язаний це
повторювати, але варто явно узгодити з бекендом формат помилок (див. розділ
«Формат помилок»), а не отримати мовчазну суміш різних конвенцій.

## Адресація за slug, не за внутрішнім id

Прод уже знає, яку сторінку йому показувати на кожному маршруті (наприклад,
маршрут «Автопарк» завжди означає сторінку `bus-park`) — ця відповідність
живе в коді прода, не в БД. Якщо API видаватиме сторінкам власний непрозорий
id (autoincrement/uuid), який стає відомим лише після першого збереження,
виникає проблема: як передати цей id проду, який про нього нічого не знає
й дізнається тільки постфактум?

**Рішення: `slug` (те, що сьогодні є іменем файлу — `bus-park`,
`about-company`...) — це основний, обов'язковий, унікальний ключ, який
редактор задає сам при створенні сторінки, і за яким сторінка адресується
всюди.** Внутрішній id (якщо він у БД бекенду взагалі є) нікому зовні не
потрібен і ніколи не покидає бекенд.

- Якщо інструментарій бекенду дозволяє — `slug` є первинним ключем напряму
  (`PUT /content/pages/{slug}` як upsert: створює, якщо немає, оновлює,
  якщо є).
- Якщо ні (CRUD-генератор наполягає на автоid) — тоді як мінімум потрібен
  окремий пошук за slug (`GET /content/pages/{slug}`, а не
  `GET /content/pages/{id}`), і slug — обов'язкове унікальне поле, яке не
  можна змінити після створення.

Завдяки цьому: (а) не існує «спочатку відправили — потім дізналися id»,
редактор одразу знає адресу нового запису (сам її придумав); (б) прод при
переході зі статичних файлів на API міняє лише URL з
`/files/theme_2/dynamic-pages/bus-park.json` на `/api/content/pages/bus-park`
— жодної нової логіки мапінгу ніде заводити не треба.

## Авторизація

Редактор не має власного логіна — його запускає (редіректом або в iframe)
хостова система бекенду, яка одразу передає готовий токен доступу в URL
(`?token=...`). Редактор читає його при старті, ставить у
`Authorization: Bearer <token>` для всіх своїх запитів і прибирає з адресного
рядка (реалізовано в `main.ts`). Для локального `npm run dev` без хоста —
`.env.local` (не в git) з `VITE_DEV_TOKEN` як заміна.

## 1. Сторінки (`/content/pages`) — ✅ готово

```
GET    /content/pages                      -> PageListItem[]   (тільки visible=true)
GET    /content/pages?includeHidden=true   -> PageListItem[]   (усі; потрібен токен)
GET    /content/pages/{slug}               -> PageContent
PUT    /content/pages/{slug}               -> upsert, body = PageContent
PATCH  /content/pages/{slug}/visibility    -> body { visible: boolean }
DELETE /content/pages/{slug}
```

```ts
interface PageListItem {
  slug: string
  title: string        // людська назва для списку сторінок, не читається продом
  visible: boolean
}
```

**2026-08-24, оновлення:** `GET /content/pages` тепер повертає точно
`{slug, title, visible}` — раніше (той самий день, раніше) відповідь ще
мала іншу форму (`{id, slug, themeId, status, sortOrder, ...}`, без
`title`, `status` замість `visible`) — той перехідний стан уже позаду,
клієнт (`ajax.ts`) лишив захисний мапінг (`item.pageId ?? item.slug`,
`status === 'published'` як запасний варіант для `visible`) про всяк
випадок, шкоди від цього немає.

```ts
interface PageContent {
  title: string
  breadcrumbs: boolean
  backButton: boolean
  hero: boolean
  blocks: unknown       // опаque JSON — дерево блоків сторінки, бек не парсить
  seo?: {                // перевизначення сайт-вайд значень з /content/settings/seo для цієї сторінки
    title?: string
    description?: string
    ogImage?: string
    noindex?: boolean    // <meta name="robots" content="noindex,follow">
  }
}
```

`visible` — показати/приховати сторінку без видалення (кнопка в редакторі
поруч із «видалити»). `PATCH .../visibility` — окремий легкий ендпойнт, а не
поле всередині `PUT`-body: приховати сторінку не повинно вимагати
пересилання всього (можливо, великого) дерева `blocks`. Прихована сторінка
не зникає з `GET /content/pages/{slug}` (редактор і далі може її
редагувати) — вона зникає тільки зі списку `GET /content/pages` без
`includeHidden`, яким має користуватись прод (меню, sitemap, список сторінок
для клієнта) — тобто прод за замовчуванням просто ніколи не побачить
приховану сторінку в переліку.

Окремий випадок — `footer-content`: технічно теж «сторінка» (`PUT/GET
/content/pages/footer-content`), але не має з'являтися у `GET /content/pages`
(це не самостійна сторінка, а вміст футера).

## 2. Налаштування (`/content/settings/{key}`)

```
GET /content/settings/global          PUT /content/settings/global          ✅ готово
GET /content/settings/palette         PUT /content/settings/palette         ✅ готово
GET /content/settings/seo             PUT /content/settings/seo             ✅ готово
GET /content/settings/menu-content    PUT /content/settings/menu-content    ⏳ ще ні
GET /content/settings/popups          PUT /content/settings/popups          ⏳ ще ні (демо: так)
```

`popups` — попапи сайту (розділ редактора «Попапи»): `{ popups: PopupModel[] }`,
де `PopupModel = { id, name, placement: 'left'|'right'|'bottom'|'center', width?,
title?: TranslatedModel, content: { type: 'section-with-free-content', children } }`.
Попап глобальний: його відкриває будь-яка кнопка будь-якої сторінки
(`action: 'popup'`, `popup: id` у блоці кнопки).

Кожен — непрозорий JSON-блоб (тіла зараз відповідають `GlobalSettingsModel` /
`Record<string,string>` / структурі меню / `SeoSettingsModel` нижче — але бек
не повинен їх типізувати, лише зберігати).

```ts
// content/settings/seo - сайт-вайд значення за замовчуванням для <title>/meta
// description/og:image. Per-сторінкові перевизначення - НЕ окремий
// ендпойнт, а поле seo? всередині самого PageContent (розділ 1) - для
// production рендер один: page.seo?.title ?? "%s".replace("%s", page.seo?.title
// ?? seoSettings.defaultTitle) і так далі, err-side завжди в бік дефолту.
interface SeoSettingsModel {
  titleTemplate: string          // напр. "%s — Virtual Dimension", %s = заголовок сторінки
  defaultTitle: string
  defaultDescription: string
  defaultOgImage: string
  siteName: string                // og:site_name
  googleSiteVerification: string  // <meta name="google-site-verification" content="...">, "" = тег не рендериться
}
```

## 3. Стилі (`/content/styles`) — ⏳ ще ні, редактор працює через фолбек

```
GET /content/styles           -> string[]         (список імен файлів)
GET /content/styles/{name}    -> text/plain (CSS)
PUT /content/styles/{name}    -> body: text/plain (CSS)
```

Набір імен файлів фіксований збіркою фронтенду (продовий код посилається на
конкретні `<link>`/`@import` за іменем) — тому без `POST`/`DELETE`, тільки
читання й заміна вмісту існуючих.

## 4. Зображення (`/content/images`) — ✅ готово

```
POST   /content/images          multipart/form-data, поле "file"   -> { path: string }
GET    /content/images/{name}   -> сам файл (image bytes)
DELETE /content/images/{name}
```

**2026-08-25, підтверджено наживо:** `path` у відповіді на `POST` — уже
готовий домен-відносний шлях, який сам містить сегмент
`/api/content/images/{хеш}.{розширення}` (наприклад
`/api/content/images/790e1a04...cefd7d.jpg`) — не гола назва файлу, як
спершу планувалось у цьому документі. Все одно не абсолютна адреса з
доменом: домен/API-база може змінитись (переїзд на інший хостинг, інше
середовище) — якщо в кожній сторінці зберігати вже готову адресу з
доменом, кожна така зміна вимагає масової міграції всього збереженого
контенту. Замість цього в `blocks` записується сам `path` як є, а домен
додається вже під час показу, на клієнті (`getImageURL()` в `ajax.ts`:
`new URL(apiBaseURL).origin + path`) — тобто зміна домену зводиться до
зміни однієї конфігурації, а не переписування даних.

Одразу після завантаження `path` записується прямо в JSON сторінки (в полі
`image`/`src`) — жодного додаткового кроку «дізнатись id» тут немає й не
повинно з'явитися.

`GET /content/images/{name}` **підтверджено публічний** (перевірено наживо
— однакова відповідь із токеном і без) — критично, оскільки картинка на
сторінці рендериться як звичайний `<img src="...">`, а туди неможливо
додати заголовок `Authorization`.

Простір імен цих адрес відрізняється від `/images/...` в самому контенті —
`/images/...` там означає «шлях, у який ще треба підставити тему»
(`/images/theme_2/...`, старий, дореальний-API формат для вже існуючого
контенту), і клієнтська логіка резолву обробляє його окремою гілкою.

## 5. Іконки — НЕ через API

Свідоме рішення: SVG-іконки не завантажуються окремим ендпойнтом. Вони
зберігаються прямо всередині `blocks` як `data:image/svg+xml;base64,...` —
рядок у полі `icon`, поряд із `.png`/`.jpg` шляхами до звичайних зображень.
SVG-іконки достатньо малі, щоб мережевий round-trip на кожну іконку того не
вартував, і це вже реалізована в редакторі поведінка для нових завантажень
(`IconEditor.vue`) — цей документ лише фіксує це рішення для бекенду:
жодного `/icons`-ендпойнта заводити не треба, `icon` — звичайний рядок
усередині опаque `blocks`.

(Технічний борг, закритий одночасно з цим документом: старі локальні демо-
сторінки `bus-park`/`about-company` досі мали `icon` як шлях до файлу
`/icons/bus-park/01.svg` — конвертовано в base64 прямо в JSON, тепер усі
іконки в тому самому форматі.)

## Формат помилок

Рекомендація (не жорстка вимога) — стандартний REST-мінімум:
- `404` — сторінки/файлу з таким slug/іменем не існує
- `409` — спроба створити сторінку з slug, який уже зайнятий
- `401`/`403` — відсутній/невалідний токен на write-ендпойнті
- `422` — валідація тіла запиту не пройшла (**на майбутнє**: коли бек почне
  перевіряти наш JSON на предмет ін'єкцій/шкідливого вмісту, а не зараз) —
  стандартний код саме для «запит зрозумілий, але вміст неприпустимий»,
  а не 420 (нестандартний, з Twitter, тут не підходить)
- тіло помилки: `{ "error": "human-readable message" }`

Явно узгодити цей формат з бекендом окремо: існуючий `/content/public/...`
(розділ 0) натомість повертає `HTTP 200` + `{"success":false,"error":"..."}`
навіть для «не знайдено» — якщо нові ендпойнти успадкують ту саму звичку
замість звичайних HTTP-кодів, клієнтський код (`ajax.ts`) це вже вміє
розпізнавати, але краще домовитись наперед, а не здогадуватись за фактом.

## Поза межами цього етапу

- `account-pages.json` — вибір варіанта
  сторінки кабінету, поки суто редакторська механіка (на проді ще
  немає самого поняття «варіант сторінки»), без відповідного API.
- Версіонування/чернетки на сервері — сьогодні редактор сам відрізняє
  «збережено локально» від «опубліковано» (кнопка «Зберегти» = виклик
  `PUT`); чи потрібен серверний драфт-шар — окреме питання, не зараз.
