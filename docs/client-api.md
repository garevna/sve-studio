# Стикування з API клієнта

**Стикувальний блок** — єдиний шар між формами сайту й API клієнта
(`packages/dock`, пакет `@sve/dock`). Форми знають лише ключі своїх полів
(`destination`, `dates`, `adults`…); куди, під якими назвами й у якому
форматі йдуть значення — це налаштування стикувального блоку:
`content/settings/client-api.json`, у редакторі — розділ «Підключення API».
Для нового клієнта змінюються лише ці налаштування, код сайту — ні.

## Що стикувальний блок робить

| Вид запиту (`role`) | Навіщо | Приклад |
| --- | --- | --- |
| `options` — **список** | варіанти для поля — рядками або **картками** (картинка, переваги, ціна) | міста для «Куди»; категорії номерів, вільні на обрані дати |
| `dates` — **вільні дати** | які дні пропонує календар і підпис під ними | вільні ночі й ціна за ніч; запитується знову, коли змінюються поля, від яких залежить, чи місяць |
| `handoff` — **передача в систему клієнта** | відвідувач іде далі — у прийом запитів клієнта: бронювання, кошик, заявку | «Знайти» → система бронювання клієнта |
| `answer` — **відповідь попапа** | відповідь попапа-питання як є | підтвердження, вибір, дата |

**Прийом запитів** (бронювання, кошик, заявка; багатокроковий візард чи одна сторінка) — **система клієнта, не наша.** Pagewright її
не пише й не знає, як вона влаштована всередині. Наша справа — передати їй
значення в тому вигляді, якого вона чекає, і повернути відвідувача на сайт.

## Передача: посилання або сесія

**Посилання** (`mode: "link"`) — відвідувач одразу переходить на адресу
системи клієнта, значення — в самій адресі:

```text
https://book.example.com/search?city=lviv&checkin=2026-12-12&checkout=2026-12-15&adults=2&return=https%3A%2F%2Fsite%2F
```

- Від клієнта: лише перелік параметрів, які приймає його система. У
  більшості систем бронювання й магазинів він уже є.
- Підходить для пошуку. Не підходить для того, чого не можна довіряти
  адресі (ціна, знижка) або чого забагато (кошик на 30 товарів).

**Сесія** (`mode: "session"`) — спершу запит в API клієнта, потім перехід
на адресу з його відповіді:

```http
POST https://api.example.com/sessions
Content-Type: application/json

{ "stay": { "destination": "lviv", "checkin": "12.12.2026", "checkout": "15.12.2026" },
  "guests": { "adults": 2, "children": 1 }, "language": "uk", "returnUrl": "https://site/" }

→ 201 { "token": "s1xlg74k" }
→ відвідувач іде на https://book.example.com/s/s1xlg74k
```

- Дані будь-якого обсягу й будови; клієнт перевіряє їх і фіксує ціну до
  переходу; відвідувач не може підправити їх в адресі.
- Від клієнта: ендпойнт створення сесії зі схемою; CORS або ключ для
  посередника (див. «Далі»).

Обидва режими — одне налаштування з перемикачем «Посилання / Сесія»: у
режимі сесії перед посиланням з'являється запит.

**iframe і чужі скрипти на сторінці** не використовуються: це ризик для
сайту й ті самі складнощі системи клієнта, які ми на себе не беремо.

## Звідки береться значення

Кожен параметр запиту (в адресі чи в тілі; `guests.adults` — вкладене поле
тіла) бере значення з одного джерела:

| `source.from` | Що | Додатково |
| --- | --- | --- |
| `field` | поле форми за ключем | `pick`: `first`, `last`, `all` (через кому), `count` — для поля з кількома значеннями (діапазон дат); `format` |
| `system` | те, що сайт знає сам: `locale`, `page`, `return` (головна сайту цією мовою), `month` (місяць календаря, `YYYY-MM`), `now` | `format` |
| `const` | сталий текст | — |
| `response` | відповідь запиту сесії, за шляхом (`token`, `data.url`) | лише в адресі переходу |

Формати: `YYYY-MM-DD`, `DD.MM.YYYY`, `MM/DD/YYYY`, `number`, `text`. Дати
сайт тримає як `YYYY-MM-DD`. Параметр без значення не надсилається взагалі.

Відносна адреса запиту відлічується від `baseUrl` документа, а без нього —
від кореня сайту (там тестовий API демо).

## Налаштування (`content/settings/client-api.json`)

```json
{
  "baseUrl": "https://api.example.com/v1",
  "requests": [
    { "id": "hotel-destinations", "role": "options", "name": "Міста з готелями",
      "call": { "url": "destinations", "method": "GET",
                "query": [{ "name": "lang", "source": { "from": "system", "value": "locale" } }] },
      "list": { "path": "items", "value": "id", "label": "{name}, {country}" } },

    { "id": "hotel-availability", "role": "dates", "name": "Вільні дати",
      "call": { "url": "availability", "method": "GET", "query": [
        { "name": "destination", "source": { "from": "field", "key": "destination" } },
        { "name": "month", "source": { "from": "system", "value": "month" } } ] },
      "result": { "path": "days", "date": "date", "hint": "{price}" } },

    { "id": "hotel-booking", "role": "handoff", "name": "Бронювання", "mode": "link",
      "target": { "url": "https://book.example.com/search", "query": [
        { "name": "checkin", "source": { "from": "field", "key": "dates", "pick": "first", "format": "YYYY-MM-DD" } },
        { "name": "return", "source": { "from": "system", "value": "return" } } ] } }
  ]
}
```

Список, який показують **картками** (номер, майстер, тариф), бере з кожного
елемента ще три речі: `image` — поле з адресою картинки (відносна — від
`baseUrl`), `details` — поле з переліком переваг (масив або рядок), `hint` —
шаблон підпису, напр. `"{perNight} €"`. Як і будь-який запит, він чекає, доки
заповнені всі поля, які читає, і запитується знову, коли вони змінюються —
тож категорії номерів приходять саме на обрані дати й гостей:

```json
{ "id": "hotel-rooms", "role": "options", "name": "Категорії номерів на ці дати",
  "call": { "url": "hotel/rooms", "query": [
    { "name": "checkin", "source": { "from": "field", "key": "dates", "pick": "first" } },
    { "name": "adults", "source": { "from": "field", "key": "adults", "format": "number" } } ] },
  "list": { "path": "items", "value": "id", "label": "{name}",
            "image": "image", "details": "perks", "hint": "{perNight} €" } }
```

Блок на сторінці називає запити за `id`: «Пошук готелю» має `destinations`,
`availability`, `roomTypes` (картки номерів, необов'язково), `booking`; обраний
номер — поле `room`. Попап — `deliver` (запит виду `answer`).

## Відповідь попапа

Попап, у якого в редакторі вибрано «Куди ще передати відповідь» (`deliver`
— id запиту виду `answer`), після відповіді надсилає:

```http
POST <адреса запиту>
Content-Type: application/json

{ "source": "popup", "id": "popup-k3x9q", "name": "Кількість місць", "kind": "prompt",
  "value": 3, "locale": "uk", "page": "/site/booking", "at": "2026-11-09T11:32:03.174Z" }
```

| Вид попапа | `value` |
| --- | --- |
| `confirm` | `true` / `false` |
| `prompt` | рядок або число — за `input.format` |
| `select` | `value` вибраного варіанта (не його назва — назва перекладається) |
| `date` | `"YYYY-MM-DD"` |

Закрито хрестиком, Esc або кліком поруч — `null`, нічого нікуди не йде.
Форми зворотного зв'язку («Повідомлення або питання», «Замовити дзвінок»,
«Своя форма») — окремий канал: `global.json → feedback.endpoint`, лист
людині, а не дані для програми.

## Демо: вигаданий клієнт

Демо підключене до вигаданого клієнта — мережі готелів «Kalyna Hotels». Він
живе окремо від сайту, як справжній: Cloudflare Worker з базою D1 на
`https://demo-api.pagewright.pp.ua` (`services/demo-client-api`, README там
же). У `client-api.json` — лише його `baseUrl` і відносні адреси.

| Адреса | Що |
| --- | --- |
| `GET /hotel/destinations?lang=uk` | `{ items: [{ id, name, country }] }` |
| `GET /hotel/availability?destination=lviv&month=2026-12` | `{ days: [{ date, price, currency }] }` |
| `GET /hotel/rooms?destination&checkin&checkout&adults&children&rooms&lang` | `{ items: [{ id, name, perks, image, perNight, total, nights, currency }] }` — категорії, вільні на ці дати й для цих гостей |
| `POST /hotel/sessions` | `{ token }` |
| `GET /hotel/sessions/<token>` | з чим створено сесію |
| `POST /hotel/bookings` | підтверджене бронювання → `{ id }` |
| `GET /hotel/book?…` | **прийом запитів клієнта** — його сторінка, куди сайт передає відвідувача |
| `GET /admin` | **адмінка клієнта**: бронювання, сесії й кожен запит — наживо |

Прийом запитів показує, що йому передали (з адреси або з сесії); «Забронювати»
записує бронювання, і воно одразу з'являється в адмінці. Адмінку відкриває
кнопка в розділі «Підключення API» — в окремому вікні, щоб тримати поруч із
сайтом. Справжня система клієнта стає на місце демо-клієнта — змінюються
лише `baseUrl`, адреси й назви параметрів.

## Що потрібно від клієнта

1. **Адреси й параметри**: списки, вільні дати, вхід у його систему (адреса
   з параметрами або ендпойнт сесії), формати дат і чисел.
2. **CORS**: запити йдуть із браузера відвідувача, тож API має дозволяти їх
   з домену сайту.
3. **Без секретів у браузері.** Ключ API, вбудований у сайт, бачить кожен
   відвідувач. Якщо API клієнта вимагає ключ — запити йдуть через
   посередника (див. «Далі»), ключ зберігається лише там.

## Далі

- Посередник (Cloudflare Worker, як Telegram-реле): ключ API клієнта,
  повтор запиту, коли API тимчасово не відповідає, журнал невдач.
- Списки, що залежать від інших полів (готелі обраного міста).
- «Форма зі схеми»: зі схеми API клієнта (JSON Schema, OpenAPI) — чернетка
  форми з потрібними полями.
- Магазин: каталог, кошик і передача кошика сесією.
